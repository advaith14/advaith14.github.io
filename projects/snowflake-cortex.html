Snowflake Cortex Analyst

Snowflake Cortex Analyst Semantic Views SQL NLP

Building a natural language analytics layer using Snowflake Cortex Analyst — letting non-technical stakeholders ask plain English questions and get correct, auditable SQL-backed answers directly from the data warehouse.

The Problem

Business stakeholders at property and asset management firms typically wait 2–3 days for ad-hoc data questions to be answered. The bottleneck isn't always the data — it's the translation layer between a business question and a SQL query. Cortex Analyst removes that bottleneck entirely: users ask questions in plain English, Cortex generates and executes the SQL, and shows both the answer and the query it ran (so technical stakeholders can audit it).

💬

Natural Language → SQL

Non-technical users ask questions in plain English. Cortex Analyst generates correct SQL against your actual schema — no prompt engineering needed.

🧠

Semantic Views

A SQL-native semantic layer that describes your data model — tables, relationships, dimensions, and metrics — so Cortex understands your business context.

🔍

Auditable by Design

Every answer comes with the SQL that generated it. Skeptical stakeholders can inspect, validate, and trust the output rather than treating it as a black box.

🏗️

Zero Extra Infrastructure

Runs entirely inside Snowflake. No external model endpoints, no data movement, no API keys per user — governed by your existing Snowflake roles.

What I Built

A real estate portfolio analytics POC for a fictional brokerage — Apex Property Group — operating across five US markets (Austin, Dallas, Houston, Phoenix, Atlanta). The data model covers property transactions, agent performance, client activity, and operating expenses.

Data Model

Star schema across two subject areas:

  • Transaction analytics — FACT_TRANSACTIONS linked to property, agent, client, and date dimensions. Metrics: commission revenue, closed deals, days on market, price-to-list ratio.
  • Expense analytics — FACT_OPERATING_EXPENSES with budget vs actual by category and market.

Data generation — realistic sample data in Snowflake

Dimension tables loaded with explicit VALUES; fact tables generated using Snowflake's GENERATOR and UNIFORM functions to produce realistic distributions:

-- Generate ~180 realistic transactions
INSERT INTO FACT_TRANSACTIONS
WITH base AS (
    SELECT
        ROW_NUMBER() OVER (ORDER BY SEQ4())              AS transaction_id,
        (ABS(MOD(RANDOM(), 20)) + 1)::NUMBER             AS property_id,
        CASE WHEN MOD(ABS(RANDOM()), 5) = 0
             THEN 'Lease' ELSE 'Sale' END                AS transaction_type,
        UNIFORM(180000, 14500000, RANDOM())::NUMBER(12,2) AS list_price_raw,
        UNIFORM(1, 120, RANDOM())::NUMBER                AS days_on_market
    FROM TABLE(GENERATOR(ROWCOUNT => 180))
), with_price AS (
    SELECT *,
        ROUND(list_price_raw * UNIFORM(0.92, 1.08, RANDOM()), -3) AS sale_price
    FROM base
)
SELECT transaction_id, property_id, transaction_type,
       list_price_raw, sale_price, days_on_market,
       ROUND(sale_price * 0.025, 2) AS commission_amount
FROM with_price;

Semantic View — teaching Cortex your data model

The semantic view is the key piece. It maps business-friendly names and metrics onto the underlying tables so Cortex Analyst knows what "agent performance" or "price-to-list ratio" means in your schema: 

CREATE OR REPLACE SEMANTIC VIEW ANALYTICS.REAL_ESTATE_SEMANTIC
  TABLES (
    DIM_PROPERTY       AS property      PRIMARY KEY (property_id),
    DIM_AGENT          AS agent         PRIMARY KEY (agent_id),
    FACT_TRANSACTIONS  AS transaction   PRIMARY KEY (transaction_id)
  )
  RELATIONSHIPS (
    MANY transaction(property_id) TO ONE property(property_id),
    MANY transaction(agent_id)    TO ONE agent(agent_id)
  )
  DIMENSIONS (
    property.market        AS property_market  COMMENT 'Metro market area',
    property.property_type AS property_type,
    agent.full_name        AS agent_name       COMMENT 'Agent full name',
    agent.market           AS agent_market
  )
  METRICS (
    SUM(transaction.commission_amount)  AS total_commission_revenue
      COMMENT 'Total commission earned on closed transactions',
    AVG(transaction.days_on_market)     AS avg_days_on_market
      COMMENT 'Average days from listing to close',
    AVG(transaction.sale_price / NULLIF(transaction.list_price, 0) * 100)
                                        AS avg_price_to_list_ratio
      COMMENT 'Sale price as % of asking — above 100 means over asking'
  );

Questions it can answer

"Which agents generated the most commission this year?" → Groups by agent_name, sums total_commission_revenue, ranks
"What is the average days on market by property type?" → Groups by property_type, returns avg_days_on_market per group
"Which markets have the highest price-to-list ratio?" → Joins property market, aggregates avg_price_to_list_ratio
"What expense categories are over budget?" → Filters on negative budget_variance in operating expenses fact
